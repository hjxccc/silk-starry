## 1. 一句话原则
CLAUDE.md 是注入每次会话的**行为契约**，不是文档。它建议性、约 80% 遵守、不保证。
写它的唯一标准：**让 Claude 下次别再犯你已经见过的那个具体错误**。

## 2. 长度与遵守率
- 根文件 **60 行理想，≤200 行硬上限**。超过 200 行遵守率断崖下降。
- 系统提示 + 工具 + MCP 在开工前已耗约 30–40k token；CLAUDE.md 要为真正重要的规则
  省注意力预算。
- **实证靠山**（arXiv 2507.11538《How Many Instructions Can LLMs Follow at Once?》，IFScale 基准）：
  即便最强前沿模型，在 **500 条指令密度下准确率也只有 68%**，且随指令增多单调下降。瓶颈**不是**
  上下文窗口装不下，而是**模型的注意力分配不过来**——所以"写得准"永远胜过"写得全"。
- **顺序也重要**（同篇论文关键发现）：模型**系统性偏向序列靠前的指令**，靠后的更易被忽略。
  因此 CLAUDE.md 里**把最关键、最易被违反的规则放最前面**（禁区、提交前必跑），背景性内容靠后。
- 一份维护良好的精简 CLAUDE.md，据社区数据每次会话可省约 40% 输入 token。
- 反直觉：太少太多都不好。目标是**写得准**，不是写得全。

### 像维护代码一样维护（Anthropic best-practices 原则，用于 audit/evolve）
- **某条反复不被遵守** → 多半是文件太长、这条被噪音淹没：先精简整体，或给该条加 `IMPORTANT`/`YOU MUST`
  强调（别滥用，见 §3）；若必须 100% 执行，转成 PreToolUse hook（CLAUDE.md 只 ~80% 遵守）。
- **不写 Claude 也会做对** → 果断删，它在白占注意力预算。
- **Claude 问的问题其实文件里写了** → 是措辞有歧义，改清楚。
- 改完用 `/memory` 看实际加载，并**观察 Claude 行为是否真的变了**来验证这条改动有没有用——
  改 CLAUDE.md 和改代码一样，要有可验证的效果，否则就是噪音。

### 减优于加（维护时的最高优先级）
维护既有 CLAUDE.md 时，**先减后加**——先删不该存在的，再补这次缺口：
- **删除优于保留**：已完成的计划、被推翻的决策、过期/已失效的条目、一次性事后复盘——直接删，别留着当噪音。
- **合并优于追加**：改已有条目，不要追加重复/近义项。
- **净增红线**：一次维护让根文件**净增 >30 行**就要警惕——多半把"叙事历史"塞进来了；规则只有"下个 AI 不看就会写错"才留。
- 这条与 §2「越短越灵」同源：维护的默认动作是**让它更短更准**，不是更全。

## 3. 该写什么 / 不该写什么

**该写（读代码看不出来的事）：**
- 不跑一遍不知道的命令——尤其"提交前必跑"组合（test / lint / typecheck / build）。
  这是官方唯一明确推荐写的内容之一。
- 与主流/默认**不同**的代码偏好（用 loguru 不用 logging；用 RQ 不用 Celery）。
  与默认一致的不用写。
- 架构约束与目录边界（"新组件放 src/components，先查有没有现成的再新建"）。
- 明确禁区（最被低估、最立竿见影：不改 `alembic/versions/`、不删看似无用的函数、
  不自动 `pip install`、不改已发布的 migration）。
- 工作方式偏好（影响 >3 文件先列计划；不确定就停下来问）。
- **踩坑 / 非显而易见行为**（Anthropic `claude-code-action` 里就有个板块叫 "Things That Will Bite You"）：
  代码里看不出、不写就会中招的行为——如"`search_code` 只是 RAG 辅助，定位优先 `glob → grep → read`"、
  "改了命令入口要同步 Main + Parser + 测试 + 文档"。这类是 CLAUDE.md 价值最高的内容之一。

**不该写（浪费且稀释重点）：**
- 目录结构、文件树、架构罗列——Claude 读代码就知道。
- 技术栈版本清单（除非有"禁止引入 X"这种边界含义）。
- 项目营销式介绍、冗长背景。
- 敏感信息（见 §9）。
- 一堆 IMPORTANT/YOU MUST——全部强调等于都不强调。

## 4. 规则准入门槛
每条规则写进去前，必须能回答：

> **"不写这条，Claude 会做错哪件具体的事？"**

答不上 → 删。这是最有效的瘦身门槛。来自实战：与其塞 12 条注水规则，不如留 6 条
精准映射你真实翻车现场的规则。

## 5. 可执行 + 配反例
规则要具体到"能自动遵守/能验证"，并尽量带一个反例对照：

| ❌ 空泛 | ✅ 可执行 |
|---|---|
| 写干净的代码 | 单个组件不超过 200 行，超了拆分 |
| 测试你的改动 | 提交前必跑 `npm run lint && npm test` |
| 注意性能 | 列表渲染必须加 key；禁止在 render 里建新对象 |
| 规范一点 | 用 2 空格缩进；文件名 kebab-case |

并解释**为什么**（"`src/generated` 是 OpenAPI 自动生成的，要改去改 schema 而非输出文件"）——
给原因比给禁令更能提升 Claude 的判断力。

## 6. 四层加载机制
官方 load order（从宽到窄，后读的更靠近 Claude、软权重略高，**不是硬覆盖**）：

| 层 | 位置 | 说明 |
|---|---|---|
| Managed policy | 系统级（`/etc/claude-code/CLAUDE.md` 等） | 最先加载，不可被排除 |
| User | `~/.claude/CLAUDE.md` | 个人全局偏好 |
| Project | `./CLAUDE.md` 或 `./.claude/CLAUDE.md` | 团队共享，提交 git |
| Local | `./CLAUDE.local.md` | 个人项目级，应 gitignore |

- 工作目录**上方**的文件启动时全量加载；**子目录**的按需懒加载（进入该目录才注入）。
- 所有发现的文件是**拼接**，不是覆盖。**不要依赖加载顺序解决冲突**，要保证规则不矛盾。
- 文件名严格大小写敏感，必须是 `CLAUDE.md`。
- `<!-- HTML 注释 -->` 会被剥离不占 token，适合给人留备注。

### 内容该写哪一层（写/生成时先路由，三层各司其职）
silk-starry 支持为三个层级写内容；动手前先判断这条内容属于谁：

| 层 | 文件 | 写什么（判据：受众 + 是否进 git） | 不该写什么 |
|---|---|---|---|
| **个人全局** | `~/.claude/CLAUDE.md` | 跨**所有项目**的个人偏好：默认包管理器、commit 语气、通用行为契约、回复偏好（"别在结尾总结"） | 项目特定的命令/约定 |
| **项目（团队）** | `./CLAUDE.md`（进 git） | 团队共享：构建/测试命令、架构约束、团队编码规范、项目禁区 | 个人偏好、密钥、本地路径 |
| **个人项目级** | `./CLAUDE.local.md`（gitignore） | 你在**这个项目**的私有偏好：本地 sandbox URL、个人测试账号、个人工作流怪癖、你的角色/熟悉度 | 团队该共享的规范（那属于 `./CLAUDE.md`） |

路由判据三连问：① 只对我、还是全团队？→ 团队进 `./CLAUDE.md`，个人进 local/user。
② 只这个项目、还是所有项目？→ 单项目进 local，跨项目进 `~/.claude/CLAUDE.md`。
③ 能进 git 吗？→ 含个人/敏感/机器特定的进 `CLAUDE.local.md`（并确保它在 `.gitignore`）。

- 写 `CLAUDE.local.md` 时，若项目 `.gitignore` 没有它，**提醒用户加上**，否则私有内容会被提交。
- 通用行为契约（如 Karpathy 12 条）建议放 `~/.claude/CLAUDE.md` 或 `.claude/rules/`，**别塞进每个项目根**。
- 三层 + 子目录都遵循同一套写作规范（≤200 行、可执行、配反例、不写敏感信息）。
- 用 `/memory` 看实际加载了哪些文件。

## 7. 拆分：rules 与 import
文件变大时，两种官方机制：
- **`.claude/rules/*.md`**：目录下所有 md 与主 CLAUDE.md 同等优先级自动加载（无需手动
  import）。可在文件顶部用 `# Glob: **/*.java` 实现**按需懒加载**（只在编辑 Java 时加载）。
  适合多团队各自维护 code-style.md / security.md。
- **`@path` import**：`@docs/api.md` 在启动时展开加载，最多 4 层递归。注意：import
  **不省 context**（会全量展开）。想省 context 用上面的 path-scoped rules。

主文件保持精简，只做"导航 + 最高频规则"，细节拆出去。

**glob 化拆分决策（B3，generate/evolve 时主动判断）**：每条规则问一句——它**只在特定文件类型/
目录下成立**，还是全项目都成立？
- 全项目成立（如"提交前必跑 X"、commit 格式）→ 留主 CLAUDE.md。
- 只对某类文件/目录成立（如"`*.vue` 组件 ≤200 行"、"`migrations/` 下不改已发布文件"）→ 拆到
  `.claude/rules/<topic>.md` 并写 `paths:`（按官方语义：Project rules 相对项目根、`/**` 可省、多模式 OR），
  这样只在编辑匹配文件时加载，省主文件预算。一个 rule 文件的 `paths` 可覆盖多个相关模式（组件+测试）。
- 判据：若一条规则塞进主文件会让"无关任务"也被迫读到它，就该 glob 化拆出去。

**易变信息用 `@import` 而非复制**（来自官方 /init 的写作规范）：会频繁变动的内容（API 文档、
配置清单、长引用）不要抄进 CLAUDE.md——抄了就会过期。改用 `@path/to/file` 引用源文件，
Claude 每次读到的都是最新版。`.claude/rules/*.md` 还支持用 `paths:` frontmatter 把规则
限定到特定文件路径（等价于本仓 `# Glob:` 写法），只在编辑匹配文件时加载。

**可选的标准开头**：官方 /init 生成的 CLAUDE.md 会以这两行开头，团队协作时可保留以示用途：
```
# CLAUDE.md
This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.
```

## 8. 推荐板块骨架
（最小集，按项目复杂度增减；具体模板见 `references/templates/`）

```markdown
# CLAUDE.md

## 项目概述
一两句话：是什么 + 技术栈。

## 构建与运行
- 安装依赖 / 启动开发 / 运行测试 / 构建生产
- 提交前必跑：<lint + test 组合>

## 代码偏好（仅列与默认不同的）
- ...

## 禁区
- 不要 ...（附原因）

## 工作方式
- 影响 >3 文件先列计划；不确定停下来问。
```

## 9. 安全红线
- **绝不**写入 API key / token / 密码 / 私钥 / 内网 IP / 数据库口令。
- 审查时把疑似敏感信息列为**最高优先级**问题（`scripts/audit.py` 会扫）。
- CLAUDE.md 通常提交 git 团队共享，泄露面大；个人/机密项放 `CLAUDE.local.md` 并 gitignore。
- **敏感文件 git 暴露（建议性）**：`scan.py` 会顺带检查 `.env`/私钥(`id_*`)/`.npmrc`/`.mcp.json`/凭证类
  文件是否被 git 跟踪或未忽略——这是 audit 只看 CLAUDE.md 看不到的盲区。**这是建议复核、非强制**：
  前端 `.env` 常只含公开 `VITE_` 变量、有些团队有意提交，属正常；只在确含密钥时才建议
  `.gitignore` + `git rm --cached` + 轮换。给别人用时**别一刀切报警**，给选择权。
- **为什么这条尤其重要**（源码实证）：Claude Code 默认的 `/init`（OLD_INIT_PROMPT）只让模型
  "记录架构 + 命令、纳入 README 重要部分"，**没有任何"别把读到的密钥/IP 写进去"的约束**——
  实测它会把 MinIO/MariaDB 明文口令、内网 IP 直接写进会提交 git 的 CLAUDE.md。新版交互式
  `/init`（NEW_INIT_PROMPT，需 feature flag）虽更精简，但同样不主动扫敏感信息。所以 generate
  时**把读到的明文凭证转写成"禁止硬编码凭证"禁区，而不是复述**，是 silk-starry 相对 /init 的硬优势。
